# Memory + Online-Learning Parity — LITFIN vs BOSSNYUMBA101

P2 of the 10-agent parity sweep. Read-only analysis of the **four-tier memory hierarchy**, the **sleep/consolidation cycle**, and the **online-learning feedback loop**.

- **LITFIN**: per-store files under `src/core/memory/` + sleep-tick at `src/core/heartbeat/sleep-tick.ts` + nightly cron at `src/app/api/cron/learning-consolidation/route.ts` + reaction-feedback at `src/core/litfin-ai/feedback/reaction-feedback.ts`.
- **BOSSNYUMBA**: kernel ports in `packages/central-intelligence/src/kernel/memory|feedback|consolidation/` + Drizzle schemas + services in `packages/database/src/schemas|services/kernel-*` + composition-root runner in `services/api-gateway/src/composition/consolidation-runner.ts` + a single POST /feedback in `services/api-gateway/src/routes/jarvis-router-factory.ts`.

Both projects expose four memory tiers (episodic / semantic / procedural / reflective) and a feedback loop. The headline divergences are: BOSSNYUMBA stores feedback but **has no UI button**, the consolidation runner exists but **has no cron/scheduler wired**, and there is **no per-turn rollup driving a kernel directive on the next turn beyond what `renderFeedbackFragment` already produces** — i.e. there is no "feedback as a system-prompt block above semantic facts" priority that LITFIN's reaction → reflective-memory pipeline writes back.

## Detailed gaps

### Gap A — Consolidation cycle has no scheduler (#19)
- **LITFIN**: `vercel.json` cron entries trigger `/api/cron/learning-consolidation` (0 3 * * *) and `/api/cron/brain-sleep-tick`. Both routes verify `CRON_SECRET`, then call `consolidateSubject(...)` / `runSleepTick(...)` for the discovered active subject set. The sleep-tick orchestrator schedules per-pass min-intervals and emission persistence (`sleep-tick.ts:79-119`).
- **BOSSNYUMBA**: `services/api-gateway/src/composition/consolidation-runner.ts:5-9` explicitly states "this module does NOT install a cron itself". No `k8s/` manifest, no `infrastructure/` directory, no `.github/workflows/` schedule, no Vercel/Render scheduler references `consolidation-runner`. The CLI guard at `:341-361` boots only when invoked directly with `node ./dist/composition/consolidation-runner.js`.
- **Behavioural diff**: No production cycle = **no semantic facts ever get extracted**, **no procedural patterns ever get detected**, **no reflective digest ever gets written**, **no expired episodic gets purged**, **no semantic confidence decay**. The memory hierarchy is "load-only" at runtime — it reads from tables that nothing populates.
- **Closure effort**: **small**. Add a Kubernetes CronJob manifest (daily 03:00 EAT for daily cycle, weekly Sunday 04:00 for weekly cycle) calling `node dist/composition/consolidation-runner.js` with `CONSOLIDATION_PERIOD_KIND={daily|weekly}` env. Mirror in `docker-compose.prod.yml` for non-k8s deploys.

### Gap B — Feedback button missing from chat UI (#22)
- **LITFIN**: Borrower / officer chat surfaces render an emoji reaction bar. Tapping fires `POST /api/borrower/messages/reactions` → `recordReactionFeedback` → fan-out to drift buffer + reflective memory + credit-mind outcome ledger. The user closes the loop in one click.
- **BOSSNYUMBA**: Backend is complete (`POST /feedback` in `jarvis-router-factory.ts:605`, `createFeedbackService` adapter, `kernel_feedback` table at migration 0122). API SDK has `recordFeedback({thoughtId, threadId, signal, rating?, correctionText?, category?})` at `packages/api-sdk/src/jarvis-client.ts:283-355`. **No `chat-ui` component mounts this method.** Source greps for `recordFeedback`, `thumbs-up`, `thumbs-down`, `ThumbsUp` in `packages/chat-ui/src/` return only test stubs. The owner-portal compiled bundle (`index-CcxKx8GD.js:895`) shows the method is bundled but never invoked from JSX.
- **Behavioural diff**: Users cannot signal feedback. `renderFeedbackFragment` will always produce an empty string, the conservative directive at `kernel.ts:1211-1215` is unreachable, and `kernel-feedback.service.rollup(...)` will report zero counts. The biggest piece of online-learning machinery built has zero traffic.
- **Closure effort**: **small**. Add a `MessageFeedbackBar` component to `packages/chat-ui/src/` that renders 👍/👎 + an optional "Tell me what was wrong" textarea after each assistant turn, persists optimistically, calls `client.recordFeedback({thoughtId: turn.thoughtId, threadId, signal, correctionText, category})`. Mount in `apps/{customer,owner,manager,admin,platform-hq}-app/*` per consistent UX.

### Gap C — Semantic search is query-free (#11)
- **LITFIN**: `semantic-store.ts:111-150` `retrieveRelevantFacts(userId, query, k=8)` — runs the user's question through `getEmbeddingService.embed(query)`, then calls Supabase RPC `match_ai_semantic_facts` (pgvector `<=>` cosine) to return the top-K facts BY RELEVANCE TO THE TURN. Falls back to recency only when the RPC isn't installed (`semantic-store.ts:143-149`).
- **BOSSNYUMBA**: `kernel.ts:1092-1107` `loadSemanticFacts(memory, tenantId, userId)` calls `memory.semantic.search({tenantId, userId, limit: 10})` with **no query** parameter — always returns the most-recently-touched 10 facts regardless of whether they're related to what the user is asking. The semantic schema has no embedding column (`kernel-memory-semantic.schema.ts:38-72`).
- **Behavioural diff**: BOSSNYUMBA leaks the "What I remember about you" fragment on every turn whether or not the facts are relevant. A user asking "what's the rent on unit 12?" gets reminded of "preferred communication: WhatsApp" — irrelevant context pollutes the prompt and wastes tokens.
- **Closure effort**: **moderate**. Add a `pgvector` extension migration, an `embedding vector(1536)` column to `kernel_memory_semantic`, embedding generation in `upsertFact` (during fact extraction in the consolidation cycle), and a new `search({query, ...})` overload using `<=>` cosine. The kernel call site at `loadSemanticFacts` then forwards `req.userMessage` as the query.

### Gap D — No multi-sink feedback fan-out (#24)
- **LITFIN**: One reaction reaches three sinks (drift buffer + reflective memory + credit-mind ledger). The drift buffer is what allows a sustained pattern of 🤔 on a persona to elevate the next nightly persona-drift probe, even though no single reaction is "negative enough" to matter on its own.
- **BOSSNYUMBA**: `kernel-feedback.service.record(...)` writes one row in `kernel_feedback` and stops. No reflective-memory shadow write, no drift-signal emission, no `kernel-action-audit` entry. The `kernel-action-audit.service.ts` exists but is not coupled to feedback.
- **Behavioural diff**: A 👎 in BOSSNYUMBA shows up in the next system prompt (good — see #25) but never propagates into the slower learning loops (drift detection, reflective lesson recording, persona-suitability scoring). Persona drift in BOSSNYUMBA can only be detected from explicit drift events (see `01-kernel-pipeline.md` step 10).
- **Closure effort**: **small**. Inside the `POST /feedback` handler at `jarvis-router-factory.ts:637`, after `svc.record(...)` succeeds, fire-and-forget: (a) for negative signals, append a `kernel-action-audit` row tagged `feedback-negative`; (b) for `correction` signals, schedule a one-shot consolidation cycle for the (tenant, user) pair with `windowDays: 1` so the correction text becomes part of next week's reflective digest.

### Gap E — Procedural promotion threshold not enforced at read time (#7)
- **LITFIN**: `procedural-store.ts:76-89` `getPromotablePatterns(userId, limit=10)` filters `observedCount >= 3` before returning. Patterns observed twice are stored but hidden until the third confirmation.
- **BOSSNYUMBA**: The consolidation cycle writes patterns at `minPatternRepeats = 2`. The kernel's `match(userMessage)` reader has no floor and returns every pattern whose keywords overlap. A pattern matched after a single (2× repeated) observation gets surfaced.
- **Behavioural diff**: BOSSNYUMBA more eagerly suggests patterns; LITFIN waits for more confirmation. Net effect on user experience: BOSSNYUMBA's autonomy loop offers "you usually do X next" earlier; LITFIN waits.
- **Closure effort**: **trivial**. Add `minInvocations` to `ProceduralMatchArgs` and have the kernel pass `3`. Or: have the kernel sort by `successRate` and cap at 3 — same UX with no schema change.

### Gap F — Declared facts producer not wired (#14)
- **LITFIN**: No declared-fact channel; every fact is extracted.
- **BOSSNYUMBA**: Schema supports `source ∈ {extracted, declared, consolidated}` (`kernel-memory-semantic.schema.ts:59-61`). The `'declared'` channel anticipates a producer like `POST /memory/declare {key, value}` that the user can hit via a "Remember this: …" UI. **Not yet built.**
- **Behavioural diff**: A user can't tell the brain anything explicitly. Everything is inferred. Conservative LLMs may decline to extract sensitive preferences without a confidence ceiling, so this is also a missing trust-signal path.
- **Closure effort**: **small**. Add `POST /memory/declare` to the jarvis router, validate `(key, value)` zod, call `memory.semantic.upsertFact({source: 'declared', confidence: 1.0})`. UI: simple form in the user's settings.

### Gap G — No emissions table / morning digest (#18)
- **LITFIN**: `brain_sleep_emissions` rows + outbox `emitThought(...)` calls let "what the brain dreamed about" reach the user's morning briefing. Consolidation that finds a new lesson can offer the user "I noticed X this week" the next morning.
- **BOSSNYUMBA**: `runConsolidationCycle` returns a `ConsolidationReport` with counters and an `errors[]` but no emission stream. The reflective digest is the only visible output — and it only surfaces if a UI explicitly renders `reflective.latest(...)`.
- **Behavioural diff**: BOSSNYUMBA's consolidation is silent. The user never hears "I learned this about your portfolio last week." LITFIN's sleep emissions become morning thoughts.
- **Closure effort**: **moderate**. Add `consolidation_emissions(id, tenantId, userId, kind, payload, createdAt)` schema + service. Inside `runConsolidationCycle`, capture each new fact / pattern / digest as an emission and persist them. Wire a morning-digest BFF route that reads the last 24h of emissions for the (tenant, user).

### Gap H — No ops dashboard for feedback health (#27)
- **LITFIN**: `app/(admin)/org-admin/intelligence/learning/*` admin pages render rolling thumbs-up/down trend, top correction categories, persona-drift signals.
- **BOSSNYUMBA**: `kernel-feedback.service.rollup(...)` returns the exact shape needed (`thumbsUp`, `thumbsDown`, `corrections`, `byCategory`, `negativeRate`) but nothing renders it.
- **Closure effort**: **small**. Add `GET /admin/kernel-feedback/rollup?sinceDays=30` to admin router, render a chart in `apps/admin-portal/`.

## Recommended order

1. **Wire the cron** (Gap A) — without it the consolidation pipeline is dead code. Add a k8s CronJob + a docker-compose alternative. ½ day.
2. **Mount the feedback UI button** (Gap B) — turn on the user-side traffic. ½ day.
3. **Multi-sink feedback fan-out** (Gap D) — so the now-flowing signals reach the reflective tier + drift. ½ day.
4. **Query-conditioned semantic search** (Gap C) — pgvector migration + embedding generation in the cycle. 1 day.
5. **Emissions table + morning digest** (Gap G) — closes the loop visually. 1 day.
6. **Procedural promotion floor at read** (Gap E) — trivial; bundle with #4. ½ hour.
7. **Declared-fact endpoint** (Gap F) — small UX win, low risk. ½ day.
8. **Admin feedback dashboard** (Gap H) — ops visibility. ½ day.

Total: ~4 dev-days to bring the memory + online-learning stack to functional parity with the LITFIN reference.

## Out of scope

- **Online tuning of model weights** — LITFIN doesn't do this either (both projects ship STATIC LLMs, the learning loop only changes the prompt context). No gap to close.
- **Federated learning across tenants** — LITFIN has hooks (`gepa-train-mutation-policy`) but they're tenant-internal even there. Out of scope for this slice.
- **Memory decay tuning** — `decayPerDay = 0.005` is a config knob; LITFIN has no decay so there's nothing to compare. Defer.
- **Embedding model selection** — pgvector + 1536-dim is the obvious starting choice for parity but is an implementation detail, not a parity gap.
- **Episodic compression / summarisation rollup** — LITFIN's reflective acts as compression. BOSSNYUMBA's TTL is the compression. Both work; no functional gap.
- **Persona drift detection** — covered in `03-identity-self.md`. Cross-references where the feedback loop *feeds* drift (Gap D) but the drift system itself is P3's slice.
